# Software Engineering

Software engineering is about building software in a planned, structured, testable, and maintainable way.

In this section, you will learn how to think beyond a single program that runs once. The focus is on practical habits that help you plan, build, test, improve, and explain software projects.

## The Simple Idea

Writing code is not the same as building software.

A small program might only need a few lines of code. A software project needs more care because it may have users, files, errors, changes, and future improvements.

Good software usually needs:

- clear planning before coding
- a sensible file and folder structure
- modules that divide the program into smaller parts
- testing to check that it works
- validation to handle bad input
- documentation so other people can understand it
- improvements after problems are found

## Learning Goals

By the end of this section, you should be able to:

- understand requirements and features
- organise project files clearly
- split programs into modules
- choose suitable data storage
- handle invalid input and errors
- test software systematically
- use simple version control
- write useful documentation
- understand a complete mini project case study

## Common Student Project Problems

| Problem | Better Habit |
|---|---|
| All code is in one file | Split the program into clear sections, functions, classes, or modules |
| Requirements are unclear | Write down the main users, goals, inputs, outputs, and features |
| There is no validation | Check user input before the program uses it |
| Testing is weak | Test normal cases, edge cases, and invalid cases |
| Data is not saved to a file | Choose a simple storage method when the project needs persistent data |
| Variable and function names are unclear | Use names that explain purpose, not just short labels |
| There is no documentation | Add short notes that explain setup, features, and important design choices |

## Suggested Study Order

1. Start with requirements and features so you know what the software should do.
2. Plan the project structure before the code grows too large.
3. Use modular design to keep each part of the program focused.
4. Decide how data will be stored and loaded.
5. Add validation and error handling before testing.
6. Test the software systematically and keep a record of results.
7. Use simple version control to track progress.
8. Write documentation that would help another student understand the project.
9. Finish by studying the mini case study as a complete example.

## Quick Check Questions

### 1. Why is writing code not the same as building software?

<details>
<summary>Answer</summary>

Writing code is one part of software development. Building software also includes planning requirements, organising files, designing modules, testing, handling errors, documenting decisions, and improving the project over time.

</details>

### 2. Why should a project be split into modules?

<details>
<summary>Answer</summary>

Modules make a project easier to understand, test, debug, and improve. Each module should have a clear responsibility.

</details>

### 3. What should you test besides normal input?

<details>
<summary>Answer</summary>

You should also test edge cases and invalid input, such as empty values, unexpected text, missing files, or numbers outside the allowed range.

</details>

### 4. Why is documentation useful in a student project?

<details>
<summary>Answer</summary>

Documentation explains what the project does, how to run it, how the files are organised, and why important design choices were made. This makes the project easier to maintain and improve.

</details>
