# Choosing a Suitable Problem

## 1. Why the Problem Choice Matters

The IA begins with a chosen problem. A strong problem gives the project direction, makes the success criteria clearer, and gives you enough opportunity to show computational thinking and programming skill.

A weak problem can make the whole IA difficult, even if you work hard later. If the problem is too simple, there may not be enough logic, data handling, or testing to discuss. If the problem is too broad, the product may become unfinished. If the idea is copied from a tutorial or template, it may not show your own design and programming decisions.

Choose a problem that can become a clear computational solution: a software product designed to solve a specific problem using programming, data, logic, testing, and evaluation.

## 2. What a Suitable IA Problem Should Have

| Requirement | What it means |
|---|---|
| Clear problem | The problem can be explained in a specific way |
| Real or meaningful context | The problem belongs to a user, group, organisation, subject area, or computing context |
| Software solution | The problem can realistically be addressed using a program |
| Sufficient complexity | The solution needs meaningful logic, data handling, algorithms, structures, or OOP |
| Feasible scope | The project can be completed within available time and skill level |
| Testable outcome | The final product can be tested against measurable success criteria |
| Student ownership | The solution shows the student's own design and programming decisions |

## 3. Good Sources of IA Problems

Good IA problems may come from:

- a real user or client
- school or club organisation
- personal workflow
- another DP subject
- a local business or community need
- a computational context or technical interest

Short example ideas:

- library borrowing tracker
- club member database
- appointment scheduler
- revision planner
- inventory tracker
- encryption/decryption utility
- study data visualiser
- simple accessibility support tool

These are starting points, not ready-made projects. Each idea still needs a clear problem, user, scope, success criteria, and enough computational complexity.

## 4. Strong vs Weak Project Ideas

| Stronger idea | Why it is stronger | Weaker idea | Why it is weaker |
|---|---|---|---|
| Library borrowing system with search, loan status, persistent storage, and validation | It has data, rules, storage, testing, and real user needs | Static library information website | It mainly displays information |
| Club member management system with roles, search, reports, and file/database storage | It involves structured data and meaningful processing | Simple contact list stored only while the program runs | It has too little complexity and no persistence |
| Revision planner that schedules tasks and adjusts priority based on deadlines | It uses logic, data, and decision-making | To-do list with only add/delete | It is too basic |
| Encryption/decryption utility with input validation and multiple modes | It applies CS knowledge and can be tested | One-button text reverser | It is too simple |
| Educational quiz game with scoring, question bank, progress tracking, and feedback | It has data handling and user progress | First level of a large unfinished game | It is incomplete and too broad |

## 5. Projects That Are Usually Too Weak

Some project ideas are usually too weak for the IA because they do not give enough opportunity to show computational thinking, programming skill, testing, and evaluation.

Projects that are usually too weak include:

- simple calculator
- cash register with only basic arithmetic
- static website or template website
- unfinished product
- first level of a game
- copied tutorial project
- database made only using wizard tools
- spreadsheet without significant coding
- program that only adds/searches/edits/deletes records temporarily in RAM
- app with no meaningful data processing
- project with no clear problem

This does not mean these topics are always impossible. It means the basic version is usually not enough. The idea would need a clearer problem, stronger data handling, meaningful logic, testing opportunities, and evidence of your own design decisions.

## 6. Projects That Are Usually Too Large

A project can also fail because it is too ambitious. A large idea may sound impressive, but if it cannot be finished, tested, and explained clearly, it becomes risky.

Projects that are usually too large include:

- full social media platform
- live multiplayer game
- large 3D game
- online payment system
- complex AI system without enough data or skill
- app that depends heavily on unreliable APIs
- system requiring real sensitive user data
- project with too many features to finish

A focused project is usually safer than a huge project. You should be able to build a working version, explain the main algorithms or logic, test the product, and evaluate it against success criteria.

## 7. Sufficient Complexity

Sufficient complexity means the project gives you enough opportunity to show real computer science skill. It does not mean making the project unnecessarily complicated.

A suitable project may include several of:

- data structures
- persistent file storage or database storage
- searching and sorting
- validation
- algorithms
- decision-making logic
- multiple modules/classes
- user roles or permissions
- reports or summaries
- meaningful testing strategy
- OOP where appropriate

Do not add random advanced features just to look impressive. Complexity should serve the problem.

## 8. Feasibility Check

- [ ] Can I build a working version in the available time?
- [ ] Do I understand the main programming techniques needed?
- [ ] Can I learn the missing techniques without the project becoming impossible?
- [ ] Can I test the final product?
- [ ] Can I avoid collecting sensitive real data?
- [ ] Can I explain why this solution is needed?
- [ ] Can I explain why existing methods are not good enough?
- [ ] Can I show my own design decisions?

## 9. Problem Statement Builder

Use this template to draft your problem statement:

```text
The current situation is [current method or process].
This causes [specific problem], especially when [condition or example].
The affected user/group is [user/group].
A computational solution is suitable because it can [main benefit 1], [main benefit 2], and [main benefit 3].
```

Example:

```text
The current situation is that a small library records book loans on paper forms.
This causes lost records and slow searching, especially when several students borrow or return books on the same day.
The affected user/group is the librarian and student library helpers.
A computational solution is suitable because it can store loan records, search books by title or borrower, and update borrowed/returned status accurately.
```

## 10. Decision Questions Before Approval

Before finalising your topic, answer these questions:

- Who is the user?
- What is the current problem?
- Why does the problem matter?
- What data will the system use?
- What processing will the system perform?
- What will be saved or loaded?
- What algorithms or logic will be needed?
- How will the solution be tested?
- What are the main risks?
- What features are essential and what features are optional?

## 11. Quick Check

1. Why is a simple calculator usually too weak?

<details>
<summary>Answer</summary>

A simple calculator usually has limited logic, little or no data handling, and few meaningful testing opportunities. It often does not solve a specific problem beyond performing basic arithmetic.

</details>

2. Why can an overly complex game be risky?

<details>
<summary>Answer</summary>

An overly complex game may take too long to finish. If most features are incomplete, it becomes difficult to test the product, explain the development clearly, and evaluate it against success criteria.

</details>

3. What does sufficient complexity mean?

<details>
<summary>Answer</summary>

Sufficient complexity means the project has enough meaningful programming, logic, data handling, structure, or algorithms to show computer science skill. It should support the problem, not just make the project look advanced.

</details>

4. Why is persistent storage often useful?

<details>
<summary>Answer</summary>

Persistent storage lets the system save data and load it again later. This often makes the product more realistic and gives you stronger opportunities for testing and evaluation.

</details>

5. Why should success criteria be considered when choosing the problem?

<details>
<summary>Answer</summary>

Success criteria help you check whether the problem can be turned into testable goals. If you cannot write clear success criteria, the problem may be too vague, too simple, or too broad.

</details>

6. Why should students avoid copying a tutorial project?

<details>
<summary>Answer</summary>

A copied tutorial project does not clearly show your own problem choice, design decisions, programming decisions, or development process. You may use sources to learn techniques, but the submitted solution must be your own work.

</details>
