# Submission Checklist

## 1. Purpose of This Checklist

This checklist helps you review your IA before final submission. Use it after the product, documentation, testing evidence, video, and appendix have been prepared.

This checklist does not replace teacher or school instructions. Always follow the latest instructions from your teacher and school.

The checklist is organised around the official IA criteria and main submission components.

## 2. Main Submission Components

| Component | What to check |
|---|---|
| Documentation / report | Covers Criteria A-E and stays within the required word limit |
| Product | Working computational solution |
| Video | Shows product functionality and examples of testing strategy; does not exceed the required time limit |
| Appendix | Includes full source code and required supporting material |
| Sources / acknowledgements | External sources, libraries, tutorials, data, images, and AI use acknowledged where required |
| Final authenticity | Work represents the student's own understanding, design, and development |

Students must follow the final submission format required by their teacher and school.

## 3. Criteria A-E Completion Check

| Criterion | Name | Final check |
|---|---|---|
| A | Problem specification | Problem, user/context, measurable requirements, success criteria, and computational context are clear |
| B | Planning | Development plan is specific, realistic, connected to success criteria, and includes resources, risks, and dependencies |
| C | System overview | System model, components, algorithms, UI/data design, and testing strategy are clear |
| D | Development | Important techniques, code excerpts, justification, testing evidence, video evidence, and appendix links are included |
| E | Evaluation | Each success criterion is evaluated using evidence, with strengths, limitations, and justified improvements |

## 4. Criterion A: Problem Specification Checklist

- [ ] I have explained the current situation.
- [ ] I have identified the user, group, organisation, or context.
- [ ] I have described a specific problem.
- [ ] I have explained why a computational solution is suitable.
- [ ] I have listed measurable solution requirements.
- [ ] I have written clear success criteria.
- [ ] My success criteria are measurable and testable.
- [ ] My success criteria are linked to the problem.
- [ ] My success criteria are not mainly subjective.
- [ ] I have explained the computational context.

## 5. Criterion B: Planning Checklist

- [ ] I have a clear chronological development plan.
- [ ] My plan covers planning, designing, developing, testing, and evaluating.
- [ ] My plan links tasks to success criteria.
- [ ] I have identified task dependencies.
- [ ] I have estimated time realistically.
- [ ] I have listed resources, tools, libraries, data, or research needs.
- [ ] I have identified risks and limitations.
- [ ] I have planned responses to important risks.
- [ ] My plan is specific to my project.
- [ ] My plan is not just a diary written after development.

## 6. Criterion C: System Overview Checklist

- [ ] I have included a system model.
- [ ] I have shown the main components and their relationships.
- [ ] I have used diagram types suitable for my project.
- [ ] I have included important algorithms.
- [ ] My algorithms are shown clearly using pseudocode, flowcharts, or natural language.
- [ ] I have included UI design or screen planning where relevant.
- [ ] I have explained data storage, tables, files, classes, or data structures.
- [ ] I have included a testing strategy.
- [ ] My testing strategy links to success criteria.
- [ ] My testing strategy includes valid, invalid, and extreme cases where suitable.

## 7. Criterion D: Development Checklist

- [ ] I have explained how the product was developed.
- [ ] My development matches the problem specification and system overview.
- [ ] I have selected important code excerpts.
- [ ] I did not paste the full source code into the main report.
- [ ] Each code excerpt is explained.
- [ ] Code excerpts link to success criteria, algorithms, or system components.
- [ ] I have justified important programming choices.
- [ ] I have included functional testing evidence.
- [ ] I have included structural testing evidence where suitable.
- [ ] My testing table includes expected and actual results.
- [ ] I have included pass/fail outcomes.
- [ ] I have evidence such as screenshots, video timestamps, console output, saved files, or database records.
- [ ] I have placed the full source code in the appendix.
- [ ] External libraries, tutorials, code snippets, or AI assistance are acknowledged where required.

## 8. Criterion E: Evaluation Checklist

- [ ] I evaluated every success criterion.
- [ ] I stated whether each criterion was fully, mostly, partly, or not met.
- [ ] I used evidence from testing, video, screenshots, saved data, or feedback.
- [ ] I explained the product's strengths.
- [ ] I explained the product's limitations.
- [ ] I linked limitations to evidence.
- [ ] I suggested specific improvements.
- [ ] My improvements are realistic.
- [ ] My improvements address real limitations.
- [ ] My conclusion judges whether the product solves the original problem.
- [ ] My evaluation is honest and evidence-based.

## 9. Video Checklist

The video should support the documentation by showing the product working and showing examples of the testing strategy.

- [ ] The video does not exceed the required time limit.
- [ ] The video shows the product running.
- [ ] The video demonstrates the main features.
- [ ] The video shows at least some success criteria being tested.
- [ ] The video includes examples of valid input.
- [ ] The video includes examples of invalid input or error handling where relevant.
- [ ] The video shows important processing, such as search, save/load, calculation, database update, or validation.
- [ ] The video is clear enough for the viewer to understand what is being demonstrated.
- [ ] The video does not reveal private or sensitive data.
- [ ] Any data shown is mock data or safe to show.

The video should not be only a tour of screens. It should demonstrate functionality and testing examples.

## 10. Appendix Checklist

The appendix should support the IA but should not replace clear explanation in the main documentation.

- [ ] Full source code is included.
- [ ] Source code is readable and complete.
- [ ] Files are clearly named.
- [ ] Code formatting is consistent.
- [ ] Important files are not missing.
- [ ] External libraries or dependencies are listed if needed.
- [ ] Test data or sample data is included where appropriate.
- [ ] Sensitive real data is not exposed.
- [ ] Any required screenshots, extended tables, or supporting materials are included only if allowed by teacher/school guidance.
- [ ] The appendix is organised so a reader can find evidence easily.

## 11. Source Acknowledgement Checklist

- [ ] I acknowledged external libraries.
- [ ] I acknowledged tutorials used to learn techniques.
- [ ] I acknowledged code snippets where used.
- [ ] I acknowledged datasets, images, icons, or media where used.
- [ ] I acknowledged AI use according to school guidance.
- [ ] I can explain all major code and design choices.
- [ ] I did not submit copied code as my own.
- [ ] I did not hide important external help.
- [ ] I used citations or references in the format required by my teacher or school.

## 12. Data and Ethics Checklist

- [ ] I considered whether consent was needed.
- [ ] I avoided collecting unnecessary personal data.
- [ ] I used mock data where real data was not necessary.
- [ ] Any real data is stored securely.
- [ ] No private data appears in the public product, video, screenshots, GitHub repo, or documentation.
- [ ] The project has an ethical purpose.
- [ ] The product does not spy on, deceive, harm, or unfairly target users.
- [ ] I have considered privacy, fairness, and possible misuse where relevant.

## 13. Final Quality Check

| Check | Question |
|---|---|
| Clarity | Can another person understand the problem, solution, and evidence? |
| Consistency | Do Criteria A-E connect to each other? |
| Evidence | Are claims supported by tests, screenshots, video, or data? |
| Completeness | Are all required components included? |
| Word limit | Is the main documentation within the required word limit? |
| Authenticity | Can I explain the code, design, and decisions myself? |
| Formatting | Are headings, tables, screenshots, and references clear? |
| Privacy | Is all displayed data safe to share? |

## 14. Last 24-hour Checklist

- [ ] Open every file needed for submission.
- [ ] Run the product from the submitted files.
- [ ] Test the main features again.
- [ ] Check that the video file opens correctly.
- [ ] Check that the appendix contains full source code.
- [ ] Check that references and acknowledgements are included.
- [ ] Check that no private data is visible.
- [ ] Check that the final document is the correct version.
- [ ] Check spelling of file names.
- [ ] Submit before the deadline.
- [ ] Keep a personal backup.

## 15. Common Final Submission Mistakes

| Mistake | Why it is risky | Safer action |
|---|---|---|
| Missing full source code | Technical evidence is incomplete | Include complete source code in appendix |
| Video only shows interface | Functionality and testing are unclear | Demonstrate main features and test examples |
| Success criteria not evaluated | Criterion E becomes weak | Evaluate every criterion with evidence |
| No actual test results | Testing evidence is incomplete | Include expected and actual results |
| Unacknowledged library or AI use | Academic integrity risk | Acknowledge sources according to guidance |
| Private data visible | Privacy risk | Use mock data or anonymise |
| Final product cannot run | Development evidence becomes weak | Test the submitted version before submission |
| Submitting wrong version | Work may be incomplete | Check filenames and final export carefully |

## 16. Final Self-confirmation

Before submission, I can explain what problem my product solves, how it was planned, how the system works, how it was developed, how it was tested, and how well it meets the success criteria. I can also explain my code and acknowledge any external help or tools I used.

## 17. Quick Check

1. What should the appendix include?

<details>
<summary>Answer</summary>

The appendix should include the full source code and any required supporting material, such as test data, sample data, extended tables, or source acknowledgements where required.

</details>

2. Why should the video show testing examples?

<details>
<summary>Answer</summary>

Testing examples show that the product was checked, not just displayed. They help prove that features work and that the testing strategy was carried out.

</details>

3. Why is actual test result evidence important?

<details>
<summary>Answer</summary>

Actual results show what really happened when the product was tested. They make the testing evidence stronger than a table that only lists expected results.

</details>

4. Why must every success criterion be evaluated?

<details>
<summary>Answer</summary>

Success criteria define what the product was meant to achieve. Evaluating each one keeps Criterion E connected to Criterion A and supports an evidence-based final judgement.

</details>

5. Why should external libraries or AI use be acknowledged?

<details>
<summary>Answer</summary>

Acknowledgement makes it clear which tools or help were used and which work is your own. It supports academic integrity and helps the reader understand your contribution.

</details>

6. Why should students test the submitted version before final submission?

<details>
<summary>Answer</summary>

The submitted version is the version that will be reviewed. Testing it helps catch missing files, broken features, wrong exports, or version mistakes before the deadline.

</details>
